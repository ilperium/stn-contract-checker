# Сверка условий договоров поставки

Прототип для специалиста по закупкам: загружаешь TXT-документы и получаешь таблицу договоров с **суммой** и **сроком поставки** на дату проверки. У каждого значения есть основание: имя файла, точная цитата и переход к абзацу исходного текста. Условия меняет только **подписанное и вступившее в силу** допсоглашение. Письма, проекты и неподписанные соглашения показываются отдельно, как несогласованные предложения.

Тестовое задание «Product Owner Semantic TextNavigator». Все компании и условия вымышлены.

## Запуск

Зависимостей нет: страница и логика написаны на чистом HTML и JavaScript и работают в браузере без сборки и без сети.

```bash
git clone https://github.com/ilperium/stn-contract-checker.git
cd stn-contract-checker
python3 -m http.server 8000      # затем открыть http://localhost:8000
```

Можно и без сервера: открыть `index.html` двойным щелчком. Загрузка своих файлов работает, кнопка «Демо-набор» скрыта, потому что браузер не даёт странице читать соседние файлы по `file://`.

Тесты (нужен Node.js 18+, пакеты не требуются):

```bash
node --test
```

## Как пользоваться

1. Задать **дату проверки** (по умолчанию 10.03.2026).
2. Нажать **«Загрузить TXT…»** и выбрать несколько файлов (или перетащить их на страницу). Для быстрой проверки есть **«Демо-набор из задания»**: он загружает те же 6 файлов из `documents/`, и они проходят тот же разбор.
3. Таблица: договор, поставщик, сумма, срок, затем колонка «Не согласовано / проверить». Под каждым значением есть ссылка «файл, абз. N»: она открывает справа исходный текст с подсвеченной цитатой. Если значение изменено допсоглашением, рядом показано прежнее значение со ссылкой на договор.
4. **Вопросы**: четыре кнопки с вопросами из задания; выбор «договор + поле»; фильтр «поставка раньше даты».
5. **Загруженные документы**: тип, статус на дату проверки и к какому договору привязан каждый файл.

Ответы на вопросы задания (демо-набор, 10.03.2026):

| Вопрос | Ответ прототипа |
|---|---|
| Срок поставки STN-101 | **30.04.2026**: изменён ДС № 1 (`02_amendment_signed.txt`, в силе с 01.03.2026), по договору было 15.04.2026. Проект ДС № 2 (10.05.2026) не учтён |
| Сумма STN-102 | **840 000 ₽**. Аванс 252 000 ₽ показан как «не является суммой договора» |
| Сумма STN-103 | **нет данных**. Лимит 600 000 ₽ показан как «не является суммой договора» |
| Поставка раньше 01.04.2026 | **STN-102** (20.03.2026). Есть несогласованное предложение поставщика перенести на 27.03.2026 (письмо). Дополнительно: по STN-101 есть неподписанный проект переноса на 10.05.2026 |

## Как принимаются решения

- **Тип документа** определяется по заголовку: «ДОГОВОР», «ДОПОЛНИТЕЛЬНОЕ СОГЛАШЕНИЕ», «ПРОЕКТ…», «ПИСЬМО…». **Статус** берётся из строки «Статус:»: «подписан(о) обеими сторонами» или «не подписан / проект». Имя файла и порядок загрузки не используются; это проверяет отдельный тест, в котором файлы переименованы и перемешаны.
- **Привязка к договору** идёт по номеру вида `ABC-123` в тексте. Если номер не найден, указывает на незагруженный договор или упомянуто несколько договоров, документ попадает в «Не привязаны — требуют проверки».
- **Применение изменений.** Допсоглашение применяется, если оно подписано обеими сторонами и дата вступления в силу (или дата подписания, если «с момента подписания») не позже даты проверки. Несколько соглашений применяются по дате вступления в силу. Подписанное, но ещё не вступившее соглашение помечается «не вступило в силу». Если подписано, а дата вступления не найдена, ставится «требует проверки».
- **Сумма**: предложение со словом «стоимость» и числом с «руб». Предложения про аванс, лимит, бюджет и с оборотом «не является» отбрасываются и показываются как «не является суммой договора».
- **Срок поставки**: предложение со словом «поставка/поставить» (но не «поставщик») и датой, предпочтительно после «не позднее / до / на». Предложения про оплату и приёмку отбрасываются.
- **Нет значения**: выводится «нет данных». Если значений несколько разных или срок задан без даты («в течение 30 дней»), ставится «требует проверки» с цитатами кандидатов. Значение не угадывается.

## Известные ограничения

- Правила рассчитаны на общий формат учебных документов: один абзац на строку, даты `ДД.ММ.ГГГГ`, сумма цифрами с «руб». Суммы только прописью, относительные сроки («через 10 дней после…»), таблицы-спецификации и сканы не разбираются: в лучшем случае будет «требует проверки», в худшем «нет данных».
- Статус подписания берётся из текста. Подлинность подписи прототип не проверяет.
- Допсоглашение воспринимается целиком: если в нём есть сумма или срок, они заменяют прежние. Частичные формулировки («увеличить на 10%») не поддерживаются.
- Данные живут только в открытой вкладке браузера и не сохраняются.

## Записка (до двух страниц)

**Для кого.** Специалист по закупкам, который ведёт десятки договоров поставки и ежедневно отвечает на вопросы «какая сумма / какой срок сейчас действует». Ему важна не скорость чтения, а уверенность: каждое число проверяется одним щелчком, а спорное явно помечено.

**Пять вопросов клиенту перед развитием**
1. Откуда приходят документы (СЭД, почта, 1С, сканы) и в каком формате на самом деле? Какая доля сканов и DOCX?
2. Кто и как фиксирует факт подписания: отметка в СЭД, ЭЦП, скан с подписями? Можно ли брать статус из системы, а не из текста?
3. Какие ещё условия сверяют регулярно (неустойка, оплата, объём, цена за единицу, спецификации) и какие из них критичны?
4. Что должно происходить при расхождении: уведомление, задача ответственному, блокировка оплаты?
5. Кто ещё пользуется результатом (юристы, бухгалтерия, руководитель закупок) и какие права доступа к договорам у разных ролей?

**Допущения**
- Документы одного общего формата: заголовок с типом, строка «Статус:», нумерованные пункты.
- Номер договора уникален и указан в каждом связанном документе.
- Сумма включает НДС так, как написано в тексте. Валюта — рубли.
- Дата проверки задаётся пользователем и не берётся из системных часов.

**Метрики**
1. **Точность без вымысла**: доля полей, где значение совпало с эталоном или честно стоит «нет данных / требует проверки», при нуле неверных уверенных значений. Неверное уверенное значение хуже пустого.
2. **Время сверки одного договора** до и после внедрения, плюс доля ответов, которые пользователь принял без открытия исходного документа целиком.

**Архитектура**

```
TXT-файлы ─▶ parseDocument ─────────▶ analyze(docs, дата) ─────────────▶ UI
 (браузер)   абзацы, предложения,      привязка по номеру договора,     таблица, вопросы,
             тип, статус, даты,        статус на дату, применение ДС,   просмотр источника
             кандидаты суммы/срока     предложения и «проверить»        с подсветкой цитаты
             └─────────────── src/extractor.js (без DOM, тестируется в Node) ──────────────┘
```

**Три ключевых решения и компромиссы**
1. **Правила вместо LLM.** Детерминированно, бесплатно, работает офлайн, цитата всегда дословная, и легко объяснить, почему выбрано значение. Цена: хрупкость к новым формулировкам. Каждый новый оборот требует правила и теста.
2. **Всё в браузере, без сервера.** Нулевая установка, документы не покидают компьютер. Цена: нет хранения, общего доступа и истории. Для 100 000 документов не подходит.
3. **Сомнение помечается явно.** При неоднозначности (несколько значений, нет даты вступления, неизвестный статус, документ не привязан) показывается «требует проверки» с кандидатами, а не лучшая догадка. Цена: больше ручной работы на краевых случаях, зато нет ложной уверенности.

**Что изменится при 100 000 документов и правах доступа.** Разбор переезжает на сервер и выполняется один раз при поступлении документа. Результат (поля, цитаты, смещения в тексте, версия правил) хранится в БД, а исходники — в хранилище с версионированием. Поиск идёт по индексу (Postgres или OpenSearch), привязку лучше брать из СЭД, а не из текста. Права проверяются на уровне договора и контрагента, причём и в выдаче, и в цитатах: нельзя показать цитату из документа, к которому у пользователя нет доступа. Для нестандартных формулировок появляется очередь ручной проверки, а LLM используется как второй извлекатель: он обязан вернуть цитату, которая затем проверяется на дословное совпадение. Нужны журнал действий и регрессионный набор размеченных документов.

**Три следующих улучшения (по приоритету)**
1. Ставка неустойки и сроки оплаты по тому же шаблону «значение + цитата + статус». Это следующий частый вопрос закупщика.
2. Экспорт таблицы в XLSX/CSV со ссылками на источники и отметкой «проверено человеком».
3. Поддержка DOCX/PDF с текстовым слоем и набор размеченных реальных документов для измерения метрики точности.

## Отчёт о вайбкодинге

**Инструмент:** Claude Code (модель Claude Opus 5.5) в приложении Claude для macOS. Агент читал ТЗ и документы, писал код и тесты, запускал их и проверял интерфейс во встроенном браузере. Решения о стеке, публикации и приоритетах принимал я.

**Характерные запросы к ИИ**
1. «Проанализируй ТЗ и 6 файлов и скажи, можно ли на их основе выполнить задачу». В ответ получил разбор ожидаемых ответов и ловушек (аванс, лимит, срок оплаты, проект ДС, письмо). Этот разбор лёг в основу тестов.
2. «Делаем публичный репозиторий на GitHub, пушим всё туда, и нужно иметь возможность запустить локально и проверить». Отсюда решение без зависимостей: статическая страница плюс `node --test`.
3. Сценарий встречи («изменим поле и загрузим новый договор») агент превратил в тест: в тесте изменена дата в договоре и добавлен новый договор STN-104.

**Ошибки ИИ и как их поймали**
- Агент запустил тесты командой `node --test tests/`. В Node 22 она падает с `Cannot find module …/tests`: аргумент воспринимается как файл. Исправлено на `node --test` с автоматическим поиском `*.test.js` и закреплено в `package.json`.
- Первая версия разбора номера договора была запутанным однострочником с проверкой `Array.isArray(m) && m.index === undefined`. При чтении кода стало ясно, что он хрупкий. Переписан в явные две ветки.
- В интерфейсе подписанное, но ещё не вступившее в силу допсоглашение получало метку «не согласовано», хотя оно согласовано. Заметили при проверке со сменой даты на 28.02.2026. Метка заменена на «не вступило в силу».

**Как проверялось.** 10 автотестов: четыре вопроса задания, статусы документов, «нет данных», неоднозначности, независимость от имён файлов и нового договора. В тестах сверяется, что каждая цитата дословно есть в указанном абзаце. Ручная проверка в браузере: загрузка через поле выбора с переименованными файлами, изменённая сумма STN-102 (910 000 ₽), новый договор, смена даты проверки.
